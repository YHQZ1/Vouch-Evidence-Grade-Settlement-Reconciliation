# Project instructions for coding agents

This file is the implementation contract for any coding agent working in Vouch.
Read the root `README.md`, `docs/product-spec.md`, `docs/architecture.md`, and
`docs/data-contract.md` before making product changes.

## Product invariant

Vouch must never represent an unproven financial relationship as verified.

## Non-negotiable engineering rules

1. Represent monetary values as integer currency subunits. Do not use `float` for
   money calculations.
2. Preserve every source record and its source-row identity. Normalization may
   derive canonical values but may not silently overwrite raw evidence.
3. Calculate settlement net from authoritative signed movement:
   `sum(credit) - sum(debit)`, grouped by settlement and balance account where
   applicable.
4. Treat UTR as strong gateway-to-bank evidence when supported by amount, timing,
   direction, and uniqueness checks.
5. Fuzzy matching generates candidates only. It cannot independently auto-clear
   a financial record.
6. An AI model may propose hypotheses and explanations. Only deterministic
   verification may change a case to a cleared status.
7. Model-reported confidence is metadata, not proof.
8. Keep ground-truth labels physically and logically outside runtime inputs.
9. Every decision must retain source lineage, reason code, rule or prompt version,
   and the input fingerprints that produced it.
10. When evidence is missing, conflicting, malformed, or out of scope, abstain and
    create an exception.

## Scope control

- Do not add money movement, ledger writes, production credentials, or external
  communication without explicit authorization.
- Do not add distributed infrastructure, a vector database, an agent framework,
  or authentication unless an accepted architecture decision requires it.
- Do not broaden the MVP beyond standard domestic settlement close without first
  updating the product specification and recording the decision.

## Quality expectations

- Prefer pure, testable domain logic over framework-bound logic.
- Add tests for all new financial invariants and failure paths.
- Include an adversarial or negative test for each auto-clear rule.
- Keep API and UI layers separate from reconciliation policy.
- Update relevant documentation and ADRs in the same change as behavior.
- Never claim performance that is not generated by the checked-in evaluation
  procedure.

## Review checklist

Before completing a change, verify:

- Can this change create a false auto-clear?
- Does it preserve raw evidence and audit lineage?
- Is its failure behavior explicit and safe?
- Can the evaluation harness exercise it without leaking labels?
- Are money, timestamps, and identifiers normalized deterministically?
- Does the documentation still describe the actual system?
